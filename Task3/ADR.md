Пояснения:

1. **АБС:**
В архитектуре предполагается разработка интеграционного сервиса (ABS Integration), который позволит не только обрабатывать сообщени из очередей Kafka, но и реализовать контроль потока обработки в зависимости от нагрузки системы АБС.
Для реализации предлагается использовать ресурсы команды разработки Интернет-банка (технология .NET Framework 4.5). Это позволит использовать технологии, которые уже есть в компании.

2. **Сайт и Call-центры:**
С сайта банка заявка передаётся в систему АБС (асинхронно через очередь) - это актуально, если на сайте указан номер телефона клиента, который есть в системе и по которому возможно рассчитать какие-то предварительные условия.
Системы Call-центров и в система АБС интегрируются между собой через ABC Queue. Таким образом:

   - информация о предварительно согласованных условиях для клиента передаётся из системы АБС в системы Call-Center асинхронно;
   - информация о результатах первичной обработки из Call-Center в систему АБС так же передаются асинхронно.

Такое решение позволит управлять количеством данных, которые доступны сотрудникам Call-центра, а так же исключит необходимость работы в нескольких системах.

1. **СМС-информирование:**
Для СМС-информирования клиента предлагается реализовать асинхронный способ отправки СМС через очереди Kafka. Для реализации используются существующая в компани технология - .NET Framwork 4.5

1. **Интернет-банк:**
Логику работы с депозитами приято решение вынести в отдельный сервис с изолированной базой данных. Реализация силами собственной команды разработки Интернет-банка (.NET Framework). Такое решение позволит начать процесс перехода к микросервисной архитектуре и обеспечить масштабирование сервисов в рамках данного функционала. Микросервис поддерживает сценарии работы с монолитным решением, обеспечивая бесшовность в работе бизнес-функций.

1. **Call-Center:**
В предлагаемом решении сделано допущение, что системы Call-центра позволяют расширять структуру заявок на звонок необходимыми атрибутами по заявкам на депозит и обеспечивать отправку команд из интерфейса пользователя в бекенд.

### <a name="_bjrr7veeh80c"></a>**Альтернативы**

1. **АБС:**
Вместо использования очередей Kafka непосредственно в системе АБС реализовать API для работы с депозитами. Очередь обработки входящих сообщений реализовать внутри системы АБС. Таким образом, получая запрос по API он записывается во внутреннюю очередь и обрабатывается асинхронного внутренними процессами. Такое решение позволяет использовать ресурсы только команды АБС и не тратить время на изучение новой технологии Kafka.

2. **Сайт и Call-центры:**
С сайта банка заявка передаётся в систему АБС. Сотрудники Call-центра обрабатывают заявки в том числе и в системе АБС. Это позволит сократить количество интеграций и реализовать логику обработки заявок в одном месте - системе АБС.

3. **СМС-информирование:**
Использовать существующие механизмы отправки СМС-уведомлений, встроенные в ядро системы. Такое решение позволит не тратить дополнительные ресурсы на реализацию.

4. **Интернет-банк:**
Поскольку система позволяет вносить изменения (кроме ядра) можно рассмотреть вариант реализации функционала непосредственно в системе Интернет-банка. Такое решение позволит использовать существующие механизмы и объекты ядра системы, а так же работу с одной базой данных.

**Недостатки, ограничения, риски**

1. **АБС:**
Использование внутренних очередей в системе АБС создаст дополнительную нагрузку на систему, а так же не гарантирует надёжность обработки входящих данных. В случае недоступности системы часть запросов может быть потеряна. К тому же, такое решение ограничивает возможности по масштабированию системы.

2. **Сайт и Call-центры:**
Предоставление доступа в систему АБС приведёт к дополнительным работам по ограничению доступа в системе для сотрудников Call-центра (особенно для партнёрского Call-центра). Кроме того, создаст дополнительные неудобства в работе сотрудников Call-центра, поскольку придётся работать в двух системах.

3. **СМС-информирование:**
Существующие механизмы отправки СМС-уведомлений встроены в системы и недоступны для развития силами собственной команды. В дальнейшем есть потребность реализовать уведомление пользователя о всех этапах обработки заявки на депозит и это может привести к дополнительной нагрузке на систему. Кроме того, использование встроенных механизмов доставки накладывает ограничение на отправку уведомлений из других систем.

4. **Интернет-банк:**
Реализация функционала в рамках монолита создаст дополнительную нагрузку на систему, хотя она и так перегружена. Кроме того, в процессе реализации разработчики могут столкнуться с проблемами внесения изменений, поскольку ядро системы изменять невозможно. Это может привести к дублированию кода.
